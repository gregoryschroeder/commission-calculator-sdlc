# Tasks: [FEATURE NAME]

**Input**: Design documents from `/specs/[###-feature-name]/`

**Prerequisites**: plan.md (required), spec.md (required for user stories), research.md, data-model.md, contracts/

**Tests**: The examples below include test tasks. Tests are OPTIONAL - only include them if explicitly requested in the feature specification.

**Organization**: Tasks are grouped by user story to enable independent implementation and testing of each story.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (e.g., US1, US2, US3)
- Include exact file paths in descriptions

## Path Conventions

- **Single project**: `src/`, `tests/` at repository root
- **Web app**: `backend/src/`, `frontend/src/`
- **Mobile**: `api/src/`, `ios/src/` or `android/src/`
- Paths shown below assume single project - adjust based on plan.md structure

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: Depends on Setup completion - BLOCKS all user stories
- **User Stories (Phase 3+)**: All depend on Foundational phase completion
  - User stories can then proceed in parallel (if staffed)
  - Or sequentially in priority order (P1 → P2 → P3)
- **Polish (Final Phase)**: Depends on all desired user stories being complete

### User Story Dependencies

- **User Story 1 (P1)**: Can start after Foundational (Phase 2) - No dependencies on other stories
- **User Story 2 (P2)**: Can start after Foundational (Phase 2) - May integrate with US1 but should be independently testable
- **User Story 3 (P3)**: Can start after Foundational (Phase 2) - May integrate with US1/US2 but should be independently testable

### Within Each User Story

- Tests (if included) MUST be written and FAIL before implementation
- Models before services
- Services before endpoints
- Core implementation before integration
- Story complete before moving to next priority

### Parallel Opportunities

- All Setup tasks marked [P] can run in parallel
- All Foundational tasks marked [P] can run in parallel (within Phase 2)
- Once Foundational phase completes, all user stories can start in parallel (if team capacity allows)
- All tests for a user story marked [P] can run in parallel
- Models within a story marked [P] can run in parallel
- Different user stories can be worked on in parallel by different team members

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup
2. Complete Phase 2: Foundational (CRITICAL - blocks all stories)
3. Complete Phase 3: User Story 1
4. **STOP and VALIDATE**: Test User Story 1 independently
5. Deploy/demo if ready

### Incremental Delivery

1. Complete Setup + Foundational → Foundation ready
2. Add User Story 1 → Test independently → Deploy/Demo (MVP!)
3. Add User Story 2 → Test independently → Deploy/Demo
4. Add User Story 3 → Test independently → Deploy/Demo
5. Each story adds value without breaking previous stories

### Parallel Team Strategy

With multiple developers:

1. Team completes Setup + Foundational together
2. Once Foundational is done:
   - Developer A: User Story 1
   - Developer B: User Story 2
   - Developer C: User Story 3
3. Stories complete and integrate independently

## Standing Rules *(agentic-sdlc kit)*

These rules supersede anything above that conflicts with them -- in particular every statement
that tests are optional or included only on request. Keep this section in the generated tasks.md,
so the analyze step can hold the task list to it.

**Tests**: NOT optional. The constitution's test-first principle requires a test-writing task
before every task that introduces real conditional logic -- including Setup and Foundational-phase
tasks, not only User Story phases. A Foundational task creating something with real behaviour (a
validator, a domain entity's mutation methods, a repository) MUST be preceded by its own
test-writing task, and that test MUST be seen failing before the implementation task starts. A
purely structural task (a DTO, a passthrough with no branching) may skip a dedicated test, but say
so explicitly in the task list rather than silently omitting one: padding coverage with a test that
asserts nothing is forbidden too, so this is a judgment to make visibly, not a box to tick by
default in either direction.

**Failure-path guards**: A task adding a test for behaviour that only matters when something goes
wrong -- a retry policy, a timeout, a fallback, an interceptor's registration -- MUST state how the
guard will be shown to fail with the guarded behaviour removed, and MUST record the observed result
in the task text once done. If it cannot be made to fail, that is a finding to record, not a task
to quietly tick. Polish MUST include a task re-verifying that each guard this feature added still
fails with its guarded behaviour removed.
*Why: the first version of a resilience fix passed its tests while doing nothing against the
incident it was written for; one of its tests could never be made to fail, and saying so is what
stopped it being mistaken for a regression guard.*

**Condition-dependent verification**: A task that manually verifies behaviour existing only under
a condition MUST name the condition and how its presence will be evidenced immediately before the
observation. "Run quickstart.md validation" is not sufficient on its own.
*Why: a cold-path check was a real verification only because the platform's own tooling reported
the dependency paused seconds beforehand; written as a bare "check the endpoint", it would have
passed against a warm system and proved nothing.*

**PR boundaries**: Every phase above (Setup, Foundational, each User Story, Polish) is a mandatory
PR boundary. End each phase with a checkpoint task: open a PR for the phase and get it merged
before starting the next phase's tasks. A single PR MUST NOT span more than one phase, however
small the combined diff, and the final phase is still its own PR. With a single reviewer, phases
run sequentially in priority order; parallel branches would compete for one person's review rather
than save time.
*Why: a feature once ran all its phases as one unbroken branch, producing a 36-file diff that had
to be reconstructed into five PRs after the fact.*

**Deploy impact**: If any task makes the application depend on something new at startup or on a
request path -- a required environment variable, a secret, a connection string, an external
service -- add an explicit task wiring it into every real deploy target (CI/CD variables,
infrastructure definitions, deploy scripts, docs), not just local configuration. Otherwise state
here, in one line, that this feature adds no runtime dependency, so the question is visibly
answered rather than silently skipped.
*Why: a feature added a required connection string and no task touched the deploy job; every
deploy crash-looped at startup for five merges before anyone noticed.*
